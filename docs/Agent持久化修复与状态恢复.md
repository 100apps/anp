# Agent 持久化修复与状态恢复

2026-10-19，本轮关闭了上一轮发现的 17 条 Agent 最终状态异常，并在重新构建的本机生产制品中验证。**恢复的是最终值；原检查点历史没有恢复。** 完整 deep_dub 生产、质量、整片 RTF 和投稿目标仍未完成。

## 原因及修复

实际环境是 `langgraph-api 0.16.1`、`langgraph-runtime-inmem 0.36.1`。上游 `Checkpointer(unpack_hook=...)` 为读取状态建立独立序列化器时，会先重新创建、读取并注册三个同名持久化字典，随后才把视图的字典改为根保存器的字典。后台刷新注册仍可能指向先前读出的磁盘副本，覆盖之后在根保存器中新增的状态。

隔离测试复现了这个顺序：写入 A 并落盘 → 读取视图 → 写入 B → 刷新 → 新进程读取。原上游能在内存中读到 B，但重启后 B 为空；修复后 A、B 均保留。

`platform/runtime/anp_platform/agent_persistence.py` 仅调整序列化视图的构造：保留上游序列化器和根保存器的持久化入口，视图共享原字典，不重新读取/注册文件，也不关闭根字典或停止后台刷新。适配限定上述固定版本，版本变化必须重新核对，不能静默套用。第三方代码没有复制进平台源码，也没有新增存储依赖。

## 数据恢复边界

17 条线程的原运行输入、数据库节点输出和 deep_dub 冻结阶段回执仍在。按原执行顺序重组最终值后，17 条全部与中断前保存的 SHA256 精确一致；两条多轮 Studio 线程同时使用了前一轮保留的输入字段和后一轮真实输出。

恢复前先备份当前状态，再逐条确认原线程空值、无历史、运行记录仍在，仅对匹配原摘要的候选写入新的恢复检查点。线程元数据记录恢复时间、方法、原摘要及源运行/节点/阶段 ID。没有调用业务节点、重跑任务、伪造旧检查点 ID、回填首次成功率或修改质量审核。最终值恢复后再次经历 Compose 重建，原 420 条最终值全部匹配。

旧检查点的时间、完整历史和中间步骤不能从一个最终摘要恢复，仍明确记为未恢复。带来源的新恢复检查点可供后续查询，但不等价于原历史。

## 备份和限制

- `.local/backups/agent-state-anomaly-20261018T1554Z/`：发现异常时的检查点和日志，保留不删。
- `.local/backups/agent-persistence-before-20261019/`：修复前状态、容器 ID、交接归档及私有部署配置。
- `.local/backups/agent-persistence-final-20261019/`：恢复后的七个持久化文件、精确恢复候选、来源及最终摘要。文件 SHA 与当前容器逐一一致，17 条恢复检查点均在备份中；这份最终备份没有另起隔离引擎做全量恢复演练，不能把摘要核对称为恢复演练。
- inmem 仍沿用上游周期刷新，未落盘前强制断电不能承诺零丢失。故障前备份、停止后的交接及可追溯恢复仍必要；本补丁不是 PostgreSQL 事务式检查点实现。

现有旧备份、旧 anp2、anp_v2 数据均保留。后续继续完整源文处理、实际模型批量执行、全片质量门禁、整片 RTF≤0.5 及 B 站发布回执，不将本轮局部验收替代整体交付。
