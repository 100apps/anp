## 鉴权边界

- Studio 的 `/project/`、`/_next/`、`/api/platform/` 等页面、资源和管理 API 与其他平台后台都经过 Supabase 管理员校验。普通业务用户不能进入，匿名请求返回 401，HTML 导航可跳转工作台登录。
- 管理写操作和 WebSocket 保留同源检查；伪造 Grafana 身份头会被移除，再由代理按当前管理员身份注入。
- Auth/Data/Storage 公共 API 按各自用途处理登录、公开对象、用户 JWT、服务密钥和 RLS，没有强制要求人的控制台 Cookie，也没有关闭上游权限。
- LiteLLM `/litellm/v1/` 和 Langfuse `/langfuse/api/public/` 保留机器密钥校验；密钥不能用于绕过管理页面的控制台登录。
- RustFS 根路径签名请求仍要求 ANP 管理员 Cookie，同时保留 S3 SigV4 校验。转发时不改签名路径或 Host。
- ANP 登录 Cookie 不发给平台；上游地址来自服务端固定配置，客户端不能指定任意目的主机。底层服务仍监听 127.0.0.1。

## 解决的问题

1. 将 Caddy 的 Auth、Data、Storage、LiteLLM API 路由迁入 Agent Server，并保留既有平台代理。Studio 使用官方根路径资源，统一入口为这些路径逐一提供代理与管理员鉴权，避免跳转内部端口。
2. 迁移 TUS 预检与 Location 修正：允许 Studio 的 `X-Source`、`X-Client-Info`，向 Storage 传递 `/storage/v1` 前缀，恢复正确的入口协议、完整端口和路径。请求体和响应继续流式转发。
3. 实测发现 LiteLLM API 可用但静态页面 404。为原生 LiteLLM 配置 `SERVER_ROOT_PATH=/litellm`，UI 在实例的可写缓存目录处理；代理上游保留同一前缀，避免改写不可变官方文件。仅自动升级本包旧默认上游，不改用户自定义外部地址。
4. 实测发现 Langfuse 凭据正确却出现 CSRF 登录失败：浏览器保留了旧根路径同名 Cookie，原代理用字典折叠后选择了错误值。现在保持浏览器发送的具体路径优先顺序，仍过滤 ANP Cookie。真实浏览器重新登录成功，并增加回归测试。
5. 启停、服务清单、配置端口、外部资源运行器、构建锁及原生验收脚本同步移除独立网关。控制台更新了单入口与平台登录策略说明。
