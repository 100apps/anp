## 本轮真实事故

历史失败回执测试错误地假设请求键跨阶段唯一。实际数据库按阶段隔离请求键；更换模型和规则产生新输入阶段后，同一个键可以产生一次新的真实计算。不能用旧键调用执行接口来证明「只读重放」。测试已改为直接检查旧尝试，不再调用模型执行入口。

该测试通过 Windows 虚拟环境启动器启动本地 CLI，120 秒测试超时结束了原 owner，但原生模型仍在。本次真实尝试 `39170840-4bbd-4240-a216-c44f90f32a84` 已完成十份内容校准和 10/44 个来源窗口；中断不是模型或质量通过，不能丢弃这段耗时或重置原运行的排队时间。

处理前确认 owner PID 20556 已不存在，不能把访问拒绝当成不存在。对模型 PID 36716 持有内核进程句柄，核对父 PID、启动时间、执行器路径及日志中的完整命令摘要，确认是本次创建的原生进程后才终止。实际退出码为 1，原日志在 `.local/backups/omni-cli-timeout-20261018T220052Z` 留存。没有停止其他计算任务。

等待原租约过期后，通过现有 `deep_dub_reconcile_device` 管理员 RPC，核对完整停止证据并释放租约。数据库仍保留运行中尝试，暴露了缺少「失败收尾」契约的问题，因此增加 021 迁移；没有直接修改生产库尝试行或取消原运行。

## 运行器保护

`NativeGuard` 复用现有 Windows Job 基础设施。原生程序以 `CREATE_SUSPENDED` 创建，归入本次新 Job、保存 PID 后才恢复唯一主线程。Job 禁止 breakaway，并启用 `KILL_ON_JOB_CLOSE`；owner 被异常终止时，由内核结束整树。正常结束也要求 Job 的活动进程数为零，才登记根进程退出和释放设备。

真实隔离测试终止 owner，持有并等待该 Job 枚举的每一个成员句柄，核实原生子进程与孙进程均终止；不只检查根 PID，也不假定树中固定只有两个进程。实际监听身份、临时凭据、取消退出及输入证据检查共 12 项通过（4.36 秒）。失联后的日志仍需明确核对和恢复，不能仅凭 Job 配置自动伪造停止回执。

本轮之后的 CLI 集成探针使用实际 Python 可执行文件及明确的工作区/依赖路径；真实执行使用与业务匹配的有界超时，工具观察超时不当成任务终态。

## 管理员收尾契约

`deep_dub_close_lost_attempt` 只允许有设备管理和任务运行权限的用户执行，并要求：

- 指定该尝试的完整、无重复租约集合；所有租约均已释放并确认实际停止。
- 停止证据来自当前管理员的 `administrator-reconciled` 核对，不能拿普通 owner 确认或别人的确认代替。
- 尝试仍是当前未完成尝试；已有成功或失败回执不可覆盖。已完成的相同收尾可以幂等读回。

收尾只记 `failed / WORKER_LOST`，输出为空，保留原排队和启动时间。owner 失联后无法恢复单调耗时，因此 `monotonic_seconds` 为 NULL，而非把墙钟差伪装成单调测量。原运行状态、质量档位、来源与原生检查点不变。错误观察进入原 outbox，不创建质量分数或审核通过。

锁顺序与正常阶段执行保持项目、任务、运行、阶段、尝试、租约的顺序；独立库实测恢复在正常任务锁后等待，不提前持有尝试行而造成锁反转。

三种入口使用同一个服务与权限：

```powershell
uv run anp deep_dub close-lost-attempt ATTEMPT_ID --lease-id LEASE_ID
uv run anp --transport http deep_dub close-lost-attempt ATTEMPT_ID --lease-id LEASE_ID
```

HTTP 为 `POST /api/apps/deep_dub/attempts/{attempt}/close-lost`，JSON 字段为 `lease_ids`。
