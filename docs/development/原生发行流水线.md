# 原生发行流水线

工作流：`.github/workflows/native-release.yml`。推送代码到 `main` 自动构建带版本的发行包；仅更新根 README 或 `docs/` 时不重复编译发行。工作流进入仓库默认分支后，也可手动运行并指定版本。Intel Mac 和 Realtime 暂不包含。

## 版本与门禁

默认版本为 `native/VERSION` 的主次版本加工作流运行编号，如 `0.3.12`；手动版本接受三段版本号及预发布后缀。标签为 `native-v<版本>`，不触发原 Docker 的 `v*` 标签发布。

- Mac 使用原生 ARM64 runner，构建、回归、独立目录和真实压缩包验收；运行进程在禁止外网及宿主依赖目录的沙箱中执行。
- Linux 使用固定 Debian 构建容器，再在 Debian 与 Alpine 两个禁用外网的干净容器中分别验收目录和真实压缩包。
- 发布阶段需要两个架构全部成功。校验六份验收回执、版本及各架构文件清单一致，再校验压缩包摘要和大小。
- 首先上传草稿 Release；逐个核对 GitHub 返回的资产 SHA256、字节数和数量，全部一致后才公开发布。

## 构建输入与运行边界

官方归档固定 URL 和 SHA256，源码使用真实 submodule 提交；Python 与 JS 依赖使用冻结锁文件。运行数据、配置、秘密和可重新生成的执行缓存不进入压缩包。每个包包含来源、文件摘要与许可证清单。

`business/` 可单独复制配置依赖地址，详见其 README。Demo 使用离线模型；通过验收不代表已验证真实模型供应商。Mac 未做 Apple notarization，其他机器的系统策略仍需要单独验收。Linux 当前干净环境覆盖 Debian 与 Alpine，不能据此宣称兼容任意 Linux。

## 故障处理

从 Actions 的失败步骤开始检查。构建日志位于构建机 `var/native/*-build.log` 等文件，功能回执位于 `var/native/evidence/`。若仅有上传后的草稿，先确认摘要错误或缺少附件的原因；不要绕过失败门禁手动公开。修复代码后重新运行，或在代码不变且外部下载暂时失败时重试失败作业。

本机验收报告与远程流水线结果分开记录。工作流文件语法正确不代表远程构建、上传或 Release 已成功。

GitHub 标准 ARM64 Mac runner 标注为 7 GB 内存、14 GB 存储。工作流仅在临时 runner 上删除非活动 Xcode 和模拟器运行时，保留当前选中的 Xcode；Linux 临时 runner 清理不参与构建的预装 SDK。实际空间和构建结果仍需以作业输出为准。参考：[GitHub 官方 runner 配置](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)。

## Mac 构建资源与缓存

DBX 使用锁定源码，以 2 个 Cargo 作业、ThinLTO 和 8 个 codegen units 构建，避免完整 LTO 在小规格 runner 上长时间链接。编译参数记录在组件构建回执中。缓存按源码配方、锁文件、运行器镜像、编译器、SDK 和工作路径隔离；仅保存组件产物及编译输入，不保存实例数据、秘密或用户配置。在功能验收前保存已编译组件，验收门禁仍完整执行。缓存失败可从头构建。

Compose 源配置回归使用显式锁定的 PyYAML，不需要 Docker CLI，也不读取开发机 .env。原生功能验收继续启动真实服务；Linux 的干净容器检查继续依赖 Docker。

草稿的新标签在公开前可能无法通过 `/releases/tags/<tag>` 找到。发布器先从认证的 Release 列表定位精确版本，再用不可变 Release ID 查询资产和公开发布；重试复用同源码草稿，补齐未上传或摘要不符的附件。已公开版本仅核验，不覆盖；同名不同源码与额外附件均拒绝发布。
