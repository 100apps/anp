# 存储与平台组件官方产物调研（2026-10-21）

## 结论与范围

在保留当前 ANP 功能、Debian slim、Linux amd64/arm64、固定版本与来源校验的前提下，可以完全不从第三方服务 Docker 镜像提取文件。优先使用官方可执行发布物、官方系统软件包、Python/npm 发布包；确无合适完整包时才从固定源码生成生产运行文件。

当前 14 个服务分为：6 个可直接使用官方可执行发布包（ClickHouse、RustFS、DBX、Auth、PostgREST、Envoy），Redis 使用官方 DEB，PostgreSQL 使用官方 Nix 缓存及完整扩展闭包，LiteLLM 使用 Python wheel，Meta 使用 npm 包，Langfuse web/worker、Studio、Storage 共 4 个服务从源码构建。这里是建议的获取方式，不是所有替换均已完成的声明。

研究以本项目版本锁为主；补查新的发布形式不等于升级当前数据库或组件。本轮未修改 Dockerfile、生成器、源码版本锁和运行配置，未停现有服务。

## 分层与代码形态

业务职责与程序语言是两个不同维度。按照本项目当前定义，Langfuse、Studio、Storage、Meta 属于第三方平台应用；ANP 自身 Workflow 和 Deep Agent 在 business/。无论把这些平台应用叫作业务层还是平台层，其安装方式由实际技术栈决定：

- Langfuse web：Node.js 24、Next.js；worker：Node.js/TypeScript，并含 Rust 原生 addon。
- Studio：Node.js、React/Next.js，本项目锁定构建使用 Node 22。
- Storage：Node.js/TypeScript，当前固定源码要求 Node >=24、npm >=11.12.1。
- Meta：Node.js/TypeScript，官方包要求 Node >=22.12、npm >=9。
- LiteLLM：Python 应用，用 uv 管理；该版本还包含 Rust 扩展。wheel 内有大量 .py 文件，安装 wheel 并不等于失去 Python 代码。

因此 uv 不能管理前四项的 Node 依赖。Node 项目应沿用自己的 pnpm-lock.yaml/package-lock.json。生产环境需要 next build/tsc/esbuild 的结果，不能将“不需要独立 ELF 二进制”理解为“只装依赖就能直接启动全部源代码”。开发模式可以运行源代码热重载，不能拿它替代生产构建。

官方依据：[Langfuse package.json](https://github.com/langfuse/langfuse/blob/v4.64.0/package.json)、[Langfuse worker 构建与 Rust addon](https://github.com/langfuse/langfuse/blob/v4.64.0/worker/Dockerfile)、[Studio package.json](https://github.com/supabase/supabase/blob/v1.26.08/apps/studio/package.json)、[Storage package.json](https://github.com/supabase/storage/blob/v1.81.0/package.json)、[Meta package.json](https://github.com/supabase/postgres-meta/blob/v0.100.0/package.json)。同时检查了本地固定提交的相同文件，10 个源码组件的 SHA 与锁文件一致。

### DBX 可以省掉当前 Rust 与 Vite 的重复构建

官方构建流程明确针对 x86_64-unknown-linux-musl 和 aarch64-unknown-linux-musl 生成 browser-static 包，使用 embed-static。包内可执行文件实际 ELF machine 分别为 62 与 183；两者均没有 PT_INTERP 和 PT_DYNAMIC。切勿误选 dbx-web_...browser-static.zip，它对应 Windows，或误选桌面 AppImage/DEB。

在现有 Debian slim 运行环境中，ARM64 官方包使用全新隔离数据目录和未发布的 44424 端口，验证 /dbx/ 首页、登录 session 和 6 个前端引用资源通过；进程与临时目录已清理。没有替换现有 DBX 或访问用户数据库。

正式替换还应覆盖数据库驱动功能差异：官方静态构建 feature 集与当前默认 cargo build 不完全相同，特别是 DuckDB sidecar、JDBC plugin 与 JVM。静态 ELF 并不自动包含每一种外部驱动。当前镜像的 JRE 不能仅因服务主程序静态化就删掉。

依据：[官方发布工作流](https://github.com/t8y2/dbx/blob/v0.6.49/.github/workflows/release.yml)、[静态包脚本](https://github.com/t8y2/dbx/blob/v0.6.49/scripts/package-web-static.sh)。AMD64 包本轮只做校验及 ELF 检查，没有在 AMD64 Linux 上执行。

### Redis 可以用官方软件包替代源码编译

Redis 8.10.2 的 GitHub release 只有 redis-full.tar.gz，它是源码包；但官方 APT 仓库另有 Debian trixie 的双架构 redis-server 与 redis-tools。因此不能仅依据 GitHub assets 推断“Redis 没有预编译包”。

本轮读取两架构 Packages.gz，下载并校验了全部 4 个 DEB，确认 ELF 架构。固定包版本均为 `6:8.10.2-1rl1~trixie1`。redis-server 依赖同版本 redis-tools，后者声明 adduser、libc6 >=2.38、libssl3t64 >=3.0.0；与最终 trixie 基础系统匹配。

ARM64 的新包在隔离进程中验证 SET/GET、VADD、vectorset module 和真实 TLS PING 均通过；TLS 使用一次性证书、未发布的 44425 端口；现有 Redis 进程、端口和持久数据未修改。建议正式构建通过签名 APT 源固定版本安装，并禁止包安装阶段自动启动服务；不要只取 redis-server 文件后遗漏运行库。

依据：[官方仓库 Release](https://packages.redis.io/deb/dists/trixie/Release)、[amd64 索引](https://packages.redis.io/deb/dists/trixie/main/binary-amd64/Packages.gz)、[arm64 索引](https://packages.redis.io/deb/dists/trixie/main/binary-arm64/Packages.gz)。本轮做包哈希验证，未重新执行 APT 签名链安装验证及 AMD64 运行验收。

## PostgreSQL：有便携二进制，但不适合无条件替换

普通 PostgreSQL 官方发行版的软件包无法自动等价于本项目 Supabase 17 的角色、初始化 SQL 和 78 项扩展集合。

Supabase 官方确实发布便携服务端包，并非只有客户端。例：v17.11.0.003-cli 有 linux-x64 与 linux-arm64 的 tar.gz，包含 postgres、initdb、psql 等。但该 portable 是 CLI 变体，固定源码里的 receipt 声明的是精简扩展集合（supautils、pg_graphql、pgsodium、supabase_vault、pg_net、pg_cron、safeupdate），不是当前 psql_17_slim + groonga 的完整集合；而且版本也不同于当前 17.6.1.136。

建议保持固定 Supabase 源码/flake.lock，以官方 Nix cache 获得两个架构的完整运行依赖闭包，连同初始化 SQL 打包；最终运行镜像不需要 Nix daemon 或编译器。缓存缺失应明确报错，或切换显式的原生 CI 源码构建任务，不默默触发数小时编译。只有用户明确接受缩减扩展后，才把 CLI portable 作为更小的配置方案评估。

依据：[实际便携发布物](https://github.com/supabase/postgres/releases/expanded_assets/v17.11.0.003-cli)、[便携包实现](https://github.com/supabase/postgres/blob/d156ba65c14694c12cc5e782bc15b9b8ed2d1376/nix/packages/postgres-portable.nix)、[固定 flake 的双架构与缓存配置](https://github.com/supabase/postgres/blob/d156ba65c14694c12cc5e782bc15b9b8ed2d1376/flake.nix)。本轮没有重新下载完整双架构 Nix 闭包，也没有迁移当前数据库。

## Python 与 npm 发布包：无需独立 ELF，也未必需要源码重建

### LiteLLM

[PyPI 1.106.0](https://pypi.org/project/litellm/1.106.0/) 提供 `cp310-abi3-manylinux_2_28_x86_64.whl` 与 `cp310-abi3-manylinux_2_28_aarch64.whl`。本轮实际下载并校验两包，每包均有 2,769 个 Python 源文件、782 个管理 UI 文件、index.html、schema.prisma、console scripts 和对应平台的 `_native.abi3.so`。

若不修改 LiteLLM 本身，推荐独立 uv 环境 + 自有锁文件/哈希 + 固定 wheel/extras，避免重复编译 Rust bridge 与 UI。需要修改源码时，继续使用固定源码 `uv sync --frozen`；这时有 Rust 构建后端是源码事实，不能认为纯 Python 安装必然免编译。

官方 wheel 含 UI 不等于 ANP 的完整安装已经自动满足：仍须核对 proxy 及当前所需 extras、Prisma CLI/engine 及生成客户端、迁移、离线启动资源和 LiteAdmin 的独立依赖。当前 Dockerfile 另装的 admin agent 不能声称已被主 wheel 覆盖。/litellm 前缀与登录、数据库操作应做替换回归。本轮仅检查包内容，没有用 wheel 全新启动整套 LiteLLM。

### Meta

官方 npm 包 `@supabase/postgres-meta@0.100.0` 已发布，repository 指向 supabase/postgres-meta。实际 tgz 通过官方 sha512 integrity，含 dist/server/server.js、format-worker.js 和全部 20 个 SQL JS 模块；SQL 已编译为 .sql.js，不能因没有 .sql 文件判断缺资源。

推荐生成专用安装清单与 package-lock.json，以 `npm ci --omit=dev` 安装固定包与完整生产依赖，直接用 Node 运行 HTTP server。无需为使用已发布 JS 再执行一次 TypeScript 构建。原生依赖（例如 profiling、解析器、格式化工具的可选平台包）应在目标架构安装，不能跨架构拷 node_modules。需要改 Meta 本身时才转回固定源码 `npm ci && npm run build`。

依据：[官方 registry 元数据](https://registry.npmjs.org/@supabase/postgres-meta/0.100.0)、[发布包](https://registry.npmjs.org/@supabase/postgres-meta/-/postgres-meta-0.100.0.tgz)、[官方源码 manifest](https://github.com/supabase/postgres-meta/blob/v0.100.0/package.json)。本轮未在全新依赖环境启动 npm 版 HTTP server，完整替换仍需 schema/tables/query、Studio 联动及读写权限回归。

## 推荐落地顺序与验收边界

1. 保持当前锁定版本，先改“获取方式”：DBX 静态包、Redis 官方 DEB、LiteLLM wheel、Meta npm。这四项有机会消除当前重复源码构建；不附带组件升级。
2. Node 与 uv 改用官方发布归档。统一 Debian 构建环境，保留源码构建阶段的原生编译器和缓存；最终运行阶段不携带编译器。
3. PostgreSQL 维持完整扩展集；Langfuse、Studio、Storage 保持来源可追溯的源码构建。拆清“下载、依赖安装、生产构建、运行配置”四种职责，但仍可使用单个 Dockerfile 和最终统一镜像。
4. 只从同一个 Dockerfile 的本项目构建阶段复制自己生成的产物是正常多阶段构建；需避免的是从第三方服务镜像提取完整应用或系统目录。正常阶段间 COPY 无需禁用。
5. 两架构原生 CI 分别验证：ELF/动态库、版本、数据库扩展、全新初始化、升级与重启持久化、四平台路径/资源/登录/实际 API。Node/Python 的原生依赖不跨架构复用。

不建议把 latest 写进可重复构建。更新任务先发现最新兼容稳定版本，生成候选 URL/摘要/源码提交，再通过验收后更新版本锁。版本兼容升级与本轮构建简化应分开评审。

- source-fingerprints.json：10 个源码组件实际 SHA 与当前锁文件一致。
- node-release-checksums.json：官方 Node 双架构归档记录。
- conclusions.json：本报告的机器可读决策与未执行项。

本轮没有构建或发布新统一镜像，没有执行 AMD64 运行验收，没有迁移已有数据库；Meta 包与 LiteLLM wheel 尚需完整服务替换验收。研究确认的是官方产物与可行获取路径，不能把部分 ARM64 探针当作整镜像验收。


## 按 ANP 实际功能重新判断必要性

本节是源码调用关系分析及精简建议，尚未执行组件删除或 reduced profile 运行验收。所谓必需以保留的功能为前提：当前两个离线业务图本身不调用四存储、Supabase API、LiteLLM 或 Langfuse；make up 把所有平台启动，是当前脚手架配置，不是两个图的执行硬依赖。

### PostgREST 的用途

PostgREST 将 PostgreSQL 的表、视图和函数暴露为 REST API，并利用数据库角色、权限与 JWT 约束访问。例如 `GET /rest/v1/orders?status=eq.paid&select=id,total` 可以读取有权限访问的记录；也支持新增、修改、删除与函数 RPC。使用 supabase-js 的 `.from(...)` 数据接口时通常依赖它。它不等于 PostgreSQL，也不是 LangGraph/Python 自定义业务 HTTP API 的必需组件。[官方说明](https://docs.postgrest.org/en/stable/)。

当前 ANP 的两个 Demo 没有调用 PostgREST，已删除的译配业务也已不再是保留理由。Studio 的核心 SQL 查询经 Meta 的 /query 完成；Studio 的 REST API 文档/接口测试等功能才会访问 REST 分支。因此 PostgREST 可以从默认 Agent 配置中去掉，代价是不再提供 Supabase 自动 REST 数据 API 及相关 Studio 功能。

### Envoy 的用途与可替代性

当前 `docker/toolbox/runtime/settings.py` 生成的 Envoy 配置只有三个路径转发：`/auth/v1/` → Auth、`/rest/v1/` → PostgREST、`/storage/v1/` → Storage。没有在此配置中启用额外的 API-key 过滤器、限流或 JWT 网关验证。ANP 的 HTTP 扩展已经承担外层平台代理，但它目前将这三个分支统一送给 Envoy；Studio 的内部 SUPABASE_URL 也指向 Envoy。

所以 Envoy 不是存储或 Agent 的必需组件，但不能现在直接删除文件而保留原路由配置。取消全部 Supabase API 时可以整个移除；保留 API 时需要同时修改 ANP 分支路由、Studio 内部访问和服务依赖，或使用较小的容器内反向代理。不能把“宿主已有代理”当作 Studio 直接可访问它的证明。

Supabase 官方网关可能承载比当前 ANP 配置更多的职责，不能把本项目的简单分流结论推广到任意完整 Supabase 部署。[官方 Envoy 网关说明](https://supabase.com/docs/guides/self-hosting/self-hosted-envoy)。

### 逐项保留条件

| 组件 | 实际保留条件 | 默认 Agent 开发配置建议 |
| --- | --- | --- |
| PostgreSQL | 业务持久化、LiteLLM 数据库、Langfuse 元数据等 | 保留；连接外部 PG 时本地进程可关闭 |
| Redis | 当前 Langfuse 队列/缓存；业务缓存为可选 | 保留 Langfuse 时保留，不能单独删掉让队列失效 |
| ClickHouse | 当前 Langfuse 分析与追踪存储 | 保留 Langfuse 时保留；不需要 Langfuse 时可一并取消 |
| RustFS | 当前 Langfuse 的 S3 事件/媒体存储及通用 S3 | 使用本机 Langfuse 时保留；外部 S3 可替代本机进程 |
| Langfuse web | 追踪 API 与管理界面 | 需要可观测性时保留 |
| Langfuse worker | 后台事件处理 | 与 web 一起保留，不能只留界面当作可用追踪平台 |
| LiteLLM | 统一模型接入、路由、配额/成本管理 | 按平台目标建议保留；直接调用供应商时可不用 |
| DBX | 数据库图形管理 | 运维可选，建议与 Studio 二选一 |
| Studio | Supabase 专用管理 UI | 用 DBX 管库时可取消；要保留其 SQL UI 则需 Meta |
| Meta | Studio 的 SQL/元数据后端 | 不用 Studio、也不用 Meta API 时可取消 |
| Auth | 注册登录、JWT、重置密码等身份能力 | 当前 ANP 工作台尚未接入它作为用户身份系统，可默认取消 |
| PostgREST | Supabase 表/视图/RPC 的自动 REST API | 当前业务未使用，可默认取消 |
| Supabase Storage | 文件元数据、JWT/RLS 权限与文件 API | 当前保留业务未使用，可默认取消；直接 S3 不等价于其权限模型 |
| Envoy | 保留 Supabase API 时提供统一入口 | 默认取消 Supabase API 时一并取消；保留 API 时先替换路由 |

Supabase Auth 不负责 DBX、Langfuse 或 LiteLLM 自己的现有登录。不能因为这些平台有登录页就认定 Supabase Auth 是它们的身份依赖。需要共享登录时应另做明确身份接入。

### Storage 的依赖需要单独纠正

当前锁定 Storage v1.81.0 使用 PostgreSQL 数据库适配器，并在进程内验证 JWT；不是每次文件请求都必须经过 PostgREST/GoTrue。ANP 当前却把启动依赖写成了 Auth、PostgREST、RustFS，并保留了 POSTGREST_URL 环境项。这些是当前配置中的依赖边，不能全部当作当前 Storage 源码的硬依赖。

如果只保留 Storage，可以进一步剥离 PostgREST 和持续运行的 Auth；前提是正确保留初始化 SQL、JWT 签发/校验约定、数据库角色、RLS 及必要 auth schema，并验证上传、下载、签名、匿名拒绝。不能仅凭源码未调用某个 HTTP 地址就宣称完整脱钩已通过。

依据：[Storage PostgreSQL 适配器](https://github.com/supabase/storage/blob/v1.81.0/src/storage/database/pg.ts)、[Storage JWT 验证](https://github.com/supabase/storage/blob/v1.81.0/src/http/plugins/jwt.ts)。Studio SQL 路径依据固定源码 `apps/studio/lib/api/self-hosted/query.ts` 的 PG_META_URL/query 调用。

### 建议的功能组合

- Agent 开发平台：4 个存储 + Langfuse web/worker + LiteLLM + DBX，共 8 个服务。取消 Studio、Meta、Auth、PostgREST、Storage、Envoy 六项。代价是明确不再提供 Supabase 平台功能；不是保留全部旧功能的无损精简。
- 同时要 Studio SQL 管理：在上述组合上增加 Studio + Meta，共 10 项；须调整原 Studio→Gateway 依赖并处理未启用的 Auth/REST/Storage 页面，不能宣称完整 Supabase UI 均正常。
- 完整 Supabase 功能：保留相关六项；这时不能按默认 Agent 的使用情况认定它们全部无用。
- 仅跑两个离线 Demo：没有运行第三方平台的业务硬依赖，但开发命令目前自动拉起容器；若提供此模式，应同步调整开发准备和验收范围。

用户随后明确要求通过 Supabase 管理业务对象，因此不采用上述 8 服务组合为默认。该组合仅作为不需要 Supabase 时的对照方案。停服务只减少运行资源，不减少统一镜像的下载体积；要减少镜像体积和构建成本，必须让精简构建目标真正排除不需要的源码阶段、运行产物和依赖。

PostgreSQL 核心不应因取消 Supabase UI 而删除；其扩展可以按未来业务需求缩减，但必须先检查现有数据库已安装/实际使用的扩展，不能为了瘦身直接删掉既有数据依赖的 .so。

PgBouncer 可执行文件当前没有对应服务进程，是额外删除候选。若取消 Studio，不再需要它专用的 Node22 运行时；若 DBX 不再支持 JDBC，可进一步去掉 JRE，但这属于明确缩减数据库驱动能力，不能静默执行。


## 最新约束：业务对象统一经 Supabase 管理

用户明确要求保留 Supabase：结构化业务对象通过 Data API/PostgREST 或受控 RPC；附件通过 Supabase Storage；用户身份与访问权限通过 Auth/JWT/RLS。业务模块不使用 psycopg 直连表做对象 CRUD，也不使用 boto3 直连 RustFS 上传、删除业务附件。数据库迁移和基础设施诊断仍是独立运维职责，不与业务运行接口混淆。

当前两个 Demo 没有持久化业务对象；本节规定后续对象模块的接入边界，不表示已经实现新的对象管理模块。business/pyproject.toml 目前仍声明 psycopg、boto3、redis，部分基础设施验收脚本依赖它们；后续可拆到工具/开发依赖，不能误删后让验收脚本无法运行。

正确访问链路：业务 → Supabase SDK/HTTP → 统一 Supabase API 入口 → PostgREST（对象）/Storage（文件）/Auth（身份）。PostgreSQL 与 RustFS 继续作为内部存储，对业务隐藏其连接串、桶实现和管理员凭据。RustFS 可以替换为其它 S3 后端，不要求业务代码随之修改。

### 此需求下的精简优先级

| 组件 | 新结论 |
| --- | --- |
| PostgREST | 保留，它正是需要的对象 CRUD/查询/RPC 数据入口 |
| Supabase Storage | 保留，提供附件、签名链接及权限 API，不让业务绕过它直连 S3 |
| Auth | 建议保留，承接用户/空间身份；JWT 与 RLS 的业务策略仍需实际设计和验证 |
| Gateway | 保留统一入口；Envoy 可替换但不是优先项目，替换必须覆盖鉴权/头处理/CORS/签名 URL 等契约，避免自写另一套不完整网关 |
| Studio | 为 Supabase 对象管理与运维界面建议保留；纯 API 运行时不是硬依赖，可选启动 |
| Meta | 保留 Studio 时保留；无 Studio 且业务不用 Meta API 时可选关闭 |
| PostgreSQL | 保留为 Supabase 内部数据库；不让业务直接连接 |
| RustFS | 保留为 Storage/Langfuse 内部 S3 后端；不让业务直接连接 |
| DBX | 与 Studio 的基础数据库管理能力重叠，优先精简候选；删除会失去它独有的多数据库驱动和管理能力 |

当前 ANP 已经没有引入 Realtime、Edge Runtime、Logflare、Vector、imgproxy、Supavisor 等完整自托管栈的其它进程，不能把它们当作本轮可删的现有组件。现有 Supabase 的六个应用进程已是较窄子集，不能承诺保留同样的对象/文件/身份/管理界面能力还能大幅减少进程。

推荐先评审 13 服务候选：当前 14 项只去掉 DBX，保留 Supabase 六项；继续按前文改进产物获取方式。若不需要可视化对象管理，可将 Studio+Meta 做按需组合，核心运行候选为 11 服务；不会改变业务使用 Supabase API 的边界。上述数量仅是服务定义数量，不是运行资源收益测量，也不是减配验收结果。

真正可持续的精简包括：去掉未使用的 PgBouncer 可执行文件；审查 DBX 独有的 JRE/字体等依赖；把开发编译器留在构建阶段；按需安装数据库扩展。现有数据库依赖的扩展、角色、迁移与数据不自动删除。

依据：[Supabase Data API](https://supabase.com/docs/guides/api)、[Supabase Storage](https://supabase.com/docs/guides/storage)、[官方网关职责](https://supabase.com/docs/guides/self-hosting/self-hosted-envoy)。前文对当前 ANP 网关“只有三条分流”的观察不等于它已经完整实现官方网关全部鉴权功能；后续业务接入时必须按实际权限模型核验。

本轮仅调整架构与精简建议，没有删除、停用或替换 Supabase、DBX 或任何存储服务。

## 已确认实施范围（覆盖前文候选建议）

用户最终确认保留 DBX，并增加 Realtime。最终为四存储、DBX、Langfuse Web/Worker、LiteLLM、Supabase Auth/PostgREST/Storage/Realtime/Studio/Meta/Envoy，共 15 个服务。删除 PgBouncer 编译与安装；Supavisor、Edge Runtime、Logflare、Vector、imgproxy 不纳入本项目运行与构建。上游完整源码 submodule 中可能保留其参考配置，不代表 ANP 安装这些服务。

产物优先：DBX browser-static、Redis 官方 DEB、ClickHouse、RustFS、Auth、PostgREST、Envoy、golang-migrate、Node22/24、uv 均使用官方固定发行产物；Meta 使用官方 npm 包和独立 package-lock.json；LiteLLM 使用官方 PyPI wheel 和独立 uv.lock。已发布包保留实际业务代码，跳过本机重复编译 UI 和原生扩展。PostgreSQL 优先上游 Nix 二进制缓存，缓存缺失时才从锁定源码构建同一扩展组合。Langfuse、Studio、Storage、Realtime 缺少满足当前部署要求的独立发行包，从固定 submodule 提交构建。

Realtime 固定 v2.144.4（5bce1ee 所属真实提交，以 versions.lock.json 的完整 SHA 为准），采用上游 Elixir/OTP 版本生成包含 ERTS 的 release，分别在 amd64/arm64 构建。内部管理界面的 pgdelta 诊断工具不在本次频道 API 范围。真实验收与未验证项以后续验收回执为准，本文不将构建配方支持等同于双架构运行通过。
