# 官方预构建产物复查

复查日期：2026-10-25。范围为 ANP 原生发行的 macOS ARM64、Linux x64，以及在 WSL 中运行同一 Linux 包。调研与独立 PoC 完成后，用户授权将 Mac Redis 官方包接入构建，源码已修改；本轮未执行新构建、整包验收或版本发布。下文 PoC 记录不能代替修改后的整包结果。

## 结论

可以明确减少一项源码编译：Mac Redis 改用 Redis 官方预编译 ZIP。Linux Redis 和 Linux DBX 已经使用官方发行包。当前仍未找到可替代 Langfuse 原生构建或 Mac DBX Web 构建的上游原生运行包。Business 前端属于本项目业务代码，继续构建；Linux NSS 适配属于本项目少量兼容代码，保留编译。

| 组件 | 当前实现 | 复查结论 |
| --- | --- | --- |
| Mac Redis | 锁定源码编译 | 官方 8.10.2 ARM64 ZIP 的独立 PoC 通过，可以替换；仍需整包回归 |
| Linux Redis | 官方 DEB 提取运行文件 | 已避免源码编译，无需更换 |

## Mac Redis：已完成最小 PoC

[Redis 官方安装文档](https://redis.io/docs/latest/install/install-redis/install-redis-on-mac-os/)除了 Homebrew formula，还列出 Redis 自己维护的 cask；[官方 cask](https://raw.githubusercontent.com/redis/homebrew-redis/master/Casks/redis.rb)给出了直接下载地址和摘要。

- 版本：8.10.2，与当前 ANP Redis 版本一致。
- ARM64 URL：`https://packages.redis.io/homebrew/redis-oss-8.10.2-arm64.zip`。
- 实际下载大小：14,197,592 字节。
- 实测 SHA256 与官方一致：`58023ce2a4c7a5c2b1e2f46c443c4ac160b207fe11d5e4f846ab995ca392e436`。
- 官方还提供 x86_64 ZIP 和摘要，但本轮没有下载或运行 Intel Mac 产物。

实际用 otool 检查 redis-server、redis-cli，二者仅链接系统 libSystem，以及 Homebrew 绝对路径下的 libssl.3.dylib、libcrypto.3.dylib。因此不能原样复制后宣称不依赖 Homebrew。

本轮在独立 PoC 目录中复用现有官方 PostgreSQL 包的两个 OpenSSL 动态库，修正相对加载路径，并在修改 Mach-O 后生成、严格校验 ad-hoc 签名；没有编译 Redis 或 OpenSSL。没有修改系统安全配置或隔离属性。

在禁止外网、禁止读取 /opt/homebrew、/usr/local、/nix 的 sandbox 中通过：

1. 启动服务、PING、SET/GET。
2. Redis 核心 Vector Set 的 VADD、VCARD。
3. AOF 持久化，停止后搬到包含中文和空格的新目录。
4. 新目录启动，普通键及 Vector Set 数据读回。

PoC 只使用当前 ANP 所需的 Redis 核心功能，没有启用 ZIP 附带的 Search、JSON、Bloom、TimeSeries 模块；这些模块的 LLVM/libomp 等依赖不因此被宣布兼容。尚未完成 ANP 全部服务的替换后回归，也未完成 TLS 功能验收。

本机证据目录：`var/native/research/official-artifacts-2026-10-25/`，主要回执为 `redis-official-inventory.json`、`redis-poc.json`。独立探针已停止，未改变现有 ANP 实例。

## Mac DBX：桌面包不能直接视为 Web 服务包

核对了 [v0.6.54 官方 Release](https://github.com/t8y2/dbx/releases/tag/v0.6.54) 的附件。Linux 有 browser-static 包，Mac 有桌面 .app/.dmg，未发现独立 Mac Web 服务端附件。

额外下载并核对 `DBX_0.6.54_arm64.app.tar.gz`：43,452,649 字节，SHA256 为 `5b6623f60261b68b03dfb0b373ec5d180f208829164dbbad92e4832019107467`。检查归档中的可执行文件，仅找到桌面入口 `DBX.app/Contents/MacOS/dbx`，没有 dbx-web sidecar。当前锁定源码的桌面入口调用 Tauri 应用，与独立 dbx-web 入口分开；不能把桌面应用当作已经可替换的无界面 HTTP 服务。

因此，保留 Mac 内嵌 /dbx/ 与纯原生运行要求时，当前仍以锁定源码构建为兜底；连接外部 Linux DBX 可以省掉 Mac 编译，但会改变本地完整包的功能边界，不默认采用。

## Langfuse：尚无适用的官方原生运行附件

通过 GitHub Release API 核对当前锁定 v4.64.0 和最新 v4.70.0，未发现独立运行附件。自动生成的源码 ZIP/tar.gz 不是编译后的服务器。官方[自托管指南](https://langfuse.com/self-hosting/deployment/docker-compose)提供容器部署路径，不等于提供可直接解压的 Mac/Linux Node 运行目录。

当前锁定源码中 `packages/native/package.json` 的 `@langfuse/native` 标记 private，构建命令调用 napi build；没有发现可直接替代该原生扩展的公开官方 npm 发行。SDK 的 PyPI/npm 包不能替代 Langfuse 服务端。

继续遵守当前原生包不从服务镜像提取运行文件的约束，不采用解包 OCI 镜像替代原生构建。源码兜底产物应按目标架构、源码提交、锁文件、构建配方和 SDK/ABI 固定缓存，只有相关输入改变才重建；这属于 ANP 自建预编译产物，不能标为上游官方二进制。

## 建议调整顺序

先将 Mac Redis 接入官方 ZIP 并完成整包回归。之后保留 Langfuse、Mac DBX 两个必要的上游源码构建兜底，把缓存拆成各组件独立的输入摘要，避免更新一个组件就重编另一组件。签名、动态库路径修正、依赖闭包组装与最终压缩仍属于必要打包步骤，不能因使用预构建包而跳过。
