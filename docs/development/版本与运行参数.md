## 8核16GB参数基线

容器资源上限8 CPU、16GiB，nofile262144，shm256MiB。PostgreSQL连接100、shared_buffers1GiB、work_mem4MiB、maintenance256MiB、checkpoint0.9、WAL压缩、慢SQL1秒、pg_stat_statements；平台连接池每个约5连接。Redis512MiB、noeviction，AOF everysec，避免BullMQ队列被LRU驱逐。ClickHouse进程内存上限4GiB、单查询1GiB、最多32并发、查询线程4、合并线程池16；投影建表内部默认校验要求合并池容量至少20，本次16×2满足。调度线程8、冷热缓存总192MiB。LF web堆1536MiB、worker1024MiB、Studio682MiB，其他Node默认512MiB。总堆预算之外仍给原生内存、数据库缓存和宿主留空间。

ClickHouse 启动预热后的内存记账曾达到约3.06GiB，3GiB上限会使小查询也被拒绝，因此提高到4GiB并重新完成四存储读写与查询烟测。

这些是共享单机的保守生产基线，不能仅凭本机烟测称为“线上最优”。参数按实际数据量和并发压测继续调整。查询上限、Node堆和Redis上限并不是进程硬隔离；整个容器16GB是硬上限。平台先停止（总30秒），存储再停止（总60秒）；PostgreSQL用快速、可恢复的SIGINT关闭，宽限150秒。日志每服务10MiB×4文件，Docker管理日志10MiB×3。

当前主机已有其他项目服务，容器8核16GB是可用上限而非独占资源，基准受宿主负载影响。默认仅绑定127.0.0.1；线上发布时在可信入口设置TLS、登录与访问控制，再显式开放端口。Supabase 保留 Studio、Meta、Auth、PostgREST、Storage、Realtime 与 Envoy 七个服务，加上四存储、DBX、Langfuse Web/Worker 和 LiteLLM，共 15 个服务。不安装 PgBouncer、Supavisor、Edge Runtime、Logflare、Vector、imgproxy。业务对象与文件统一经 Supabase API 管理；数据库与 S3 仅为内部基础设施。

## Realtime 配置

Realtime 使用独立 UID 20015、容器内端口 4100，依赖 PostgreSQL 与 Auth。对外经现有网关和业务代理访问 `/supabase/realtime/v1/`，不新增宿主端口。WebSocket 路径映射到上游 `/socket/websocket`，广播路径映射到 `/api/broadcast`；不暴露租户管理 API 和 Realtime 内部管理界面。

PostgreSQL 启用 `wal_level=logical`、10 个复制槽和 WAL sender，并设置每槽 WAL 保留上限 1GiB。默认 publication `supabase_realtime` 不自动纳入所有业务表，需显式选择订阅表及配置 RLS。服务启动执行上游迁移与单租户种子。新增凭据写入已有私有配置，保留原有服务密码和数据。Realtime 使用上游自托管的数据库管理角色完成迁移和复制，业务用户仍通过 JWT/RLS 访问。

未打包 Realtime 内部管理界面使用的 pgdelta 诊断工具；频道、CDC、广播、Presence 不依赖它，不对外提供该内部管理界面。

`make realtime-check` 验证真实 Auth 登录、双用户对象 CRUD/RLS、CDC 隔离、广播与在线状态，隔离测试表和用户在结束后清理。`make acceptance` 包含同一检查。DELETE 事件遵循 Supabase 上游限制：[删除后无法按原行进行 RLS 检查](https://supabase.com/docs/guides/realtime/postgres-changes#receiving-old-records)，启用 RLS 时旧记录只包含主键；不要将删除通知视为对象访问授权，读取仍通过 Data API/RLS。

Studio 构建时禁用 Edge Functions 与 Logs 导航，运行时也通过官方 `ENABLED_FEATURES_LOGS_ALL=false` 关闭日志入口，避免显示本项目未部署的服务。Realtime、对象、认证和文件管理入口保留。

DBX、LiteLLM、Meta、PostgREST 只依赖官方发行包，不再要求检出对应源码。锁中的 `upstream_source_sha` 作为来源记录，实际使用产物以 URL/校验值或 npm、uv 锁文件为准。需要编译的组件及 Auth 迁移仍使用真实 submodule。

辅助构建工具 cargo-about 0.9.2、cargo-auditable 0.7.7 使用官方双架构 musl 静态发行包，URL 与 SHA256 位于 `docker/build/tools.lock.json`；构建时运行 cargo-about 版本检查及 cargo-auditable 的 Cargo 集成检查，不再通过 cargo install 编译。独立构建工具锁避免更新辅助工具时使无关服务的下载缓存失效。

本机 ARM64 仿真构建 AMD64 时，Realtime 曾出现 `Module.put_attribute` 的 JIT 仿真兼容错误。可显式传构建参数 `REALTIME_BUILD_ERL_AFLAGS=+JMsingle true`，仅影响 Realtime 构建阶段；原生双架构 CI 默认不使用此参数。依据 [Elixir 官方问题记录及维护者建议](https://github.com/elixir-lang/elixir/issues/13669)。是否有效以本次实际重建结果为准，不等价于原生 AMD64 运行验收。

Langfuse Web 的生产打包与独立 `pnpm --filter web run typecheck` 顺序执行，两者均为构建通过条件。使用上游已有 `NEXT_IGNORE_BUILD_ERRORS=true` 仅取消 Next 进程内的重复检查，紧接着运行完整独立检查，不跳过类型校验；避免 Next 打包进程约 7GB 与检查进程约 6GB 同时驻留。此为构建资源安排调整，结果仍以实际构建回执为准。
