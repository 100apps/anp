# 镜像体积与构建方式

> 本页为 Realtime 改造前的历史体积和验收记录。新方案为 15 个服务、移除 PgBouncer，并切换官方发行包；新镜像体积需单独实测。

2026-10-21 本机 linux/amd64 实测，保持14个服务、完整PostgreSQL扩展、Redis内置vectorset、Java及LiteLLM附属工具。

| 版本 | Docker本地占用 | 分发内容 |
| --- | ---: | ---: |
| 最初完整镜像 | 10.98GB | 约2.28GB |
| 上一轮优化镜像 | 8.72GB | 约1.42GB |

Docker Desktop的containerd存储同时保存压缩内容和展开层，因此下载大小与本地占用不能混为一谈。本轮本地占用比最初降低约22%，比上一轮降低约2%；采用相同Zstd口径的导出包比上一轮缩小约4.6%。全功能镜像展开后压到1GB不现实，单个基础镜像的小体积不能代表所有应用安装后的体积。

## 本轮构建

唯一入口为docker/toolbox/Dockerfile，最终基于debian:trixie-slim。ClickHouse、RustFS、Auth、PostgREST、Envoy优先取官方固定版本产物并校验SHA256；其余在同文件的构建阶段编译。不再使用本机已有anp组件镜像作为输入。PostgreSQL保留Supabase固定源码的Nix运行闭包与全部扩展，Storage统一为glibc运行环境。

生产产物清理源码映射、测试文件、安装缓存与编译工具；对相同内容硬链接去重，保留动态加载路径和许可文件。构建清理报告记录删除约662MB逻辑文件、去重约358MB逻辑文件；这两项不能直接当作Docker磁盘回收量相加。最后复制到新的Debian阶段，避免已删文件残留于旧层，正式构建使用Zstd压缩。

扁平化有利于完整交付包体积，但更新一个组件也可能重新传输大层。需要频繁独立升级组件时，可重新评估拆镜像或保留应用分层。

## 实测导出

正式构建索引：`sha256:acac63e4b3a7aed45676488082f541c1335dd393079582966de0bf8a5b456cea`。

- 文件：`var/images/anp-toolbox-acac63e4b3a7-linux-amd64.tar.zst`
- 字节数：`1353524475`
- SHA256：`91fd116bca0647d30e2d14f02b4de52333201340a108cd1cd3a91834b0ff0b8e`

```sh
make image-size
make image-export
docker load -i var/images/anp-toolbox-acac63e4b3a7-linux-amd64.tar.zst
# 根.env设置ANP_IMAGE=anp/toolbox:local
make up
```

导出为流式处理，不生成巨型未压缩中间包。包只含镜像，不含/data，迁移时需要单独备份数据根及原配置凭据。单平台导出会改变外层索引，比较内容时核对运行配置与RootFS，不能只比较索引ID。[体积证据](../acceptance/history/pre-cleanup/debian-image-size.json)保留各轮的实际字节数。

linux/arm64的大小与原生验收结果以对应GitHub Actions产物为准，不用amd64结果代替。

当前 `make image-export` 的新导出文件统一写入 `var/exports/`；上文 `var/images/` 为历史交付记录。
