# ANP2 三层可插拔架构与组件部署方案（设计记录）

实施状态与最终版本以 [README](../README.md)、[兼容性记录](../docker/compatibility.yaml) 和 [本地验收](本地验收.md) 为准；以下保留设计时的候选与边界讨论。

日期：2026-10-19。状态：已核对部分官方版本约束的设计方案；未创建运行配置、镜像或启动服务。本版取代“三层各一个大镜像”的方案。

## 1. 确定的架构边界

保留 storage、platform、business 三个逻辑层，运行时按独立服务部署。所有 Docker 配置集中在 docker/；根 compose.yaml 是固定的组合入口。

- storage：PostgreSQL、Redis、ClickHouse、RustFS 各一个服务，优先使用兼容的官方镜像，不为包装而新增 Dockerfile。
- platform：DBX、Langfuse、LiteLLM、Supabase 以真实 submodule 为源码依赖，按服务构建生产镜像。Supabase 由多个服务组成，不合装为大容器。
- business：uv 管理的 Python 业务、LangChain 体系、HTTP 扩展、shadcn/ui 前端。生产可由一个业务镜像同时提供 API 与前端静态文件。
- 平台与业务依赖连接契约，不假设下层必须是本地容器。每种存储可独立选择本地或外部，平台本身也可以切换远端实例。
- 更新组件修改其源码 SHA、镜像锁定值或运行配置；稳定接口下不改变根 Compose 的服务定义。

独立服务允许共享镜像。例如 Langfuse web 和 worker 可使用同一个包含两种生产运行产物的组件镜像，通过不同命令各运行一个容器；同组件镜像统一升级，不在一个容器里启动两个服务。若上游产物更适合分镜像，也按同一源码版本成组发布和升级。

versions.env 保存最终镜像的精确引用；submodule SHA 由 Git gitlink 记录，组件构建制品携带源码身份。compatibility.yaml 记录约束和实测结果，不重复充当另一套镜像锁文件。Compose 可以在根入口将 versions.env 作为插值默认源，允许私有 .env 或 shell 显式覆盖；不把镜像变量误放进仅注入容器进程的 service env_file。

## 3. 可插拔连接：本地和外部是同一种契约

### 3.1 存储与平台都可以替换

| 资源 | 本地 | 外部 |
| --- | --- | --- |
| PostgreSQL | local-pg profile 启动 postgres | 关闭该 profile，消费者连接外部库 |
| Redis | local-redis profile | 外部 Redis URL、ACL 与 TLS 参数 |
| ClickHouse | local-clickhouse profile | 外部查询与迁移端点、账号、TLS |
| S3 | local-s3 profile 启动 RustFS | S3 endpoint、region、bucket、凭据与寻址模式 |
| LiteLLM | litellm profile | 业务配置远端模型网关地址与凭据 |
| Langfuse | langfuse profile | 业务配置远端 Langfuse 地址与项目 Key |
| Supabase | supabase profile | 业务配置已有 Supabase API 地址与凭据 |

两种 Supabase 替换必须分清：

1. **只替换 PG**：本地仍运行 Auth/REST/Studio 等 Supabase 服务，只把其数据库放到外部。
2. **替换整个 Supabase**：业务连接已有 Supabase API；不运行本地 Supabase 组件，也不需要通过本地服务直连该平台的 PG。

### 3.2 连接配置只维护消费者实际需要的值

不把一个通用 PG URL 生硬复用给所有服务。Langfuse、LiteLLM、Agent Server 分别使用独立数据库和受限账号。Supabase 内部角色也按组件所需配置，必要时使用专门的初始化管理凭据。

示意：

```dotenv
# Langfuse 私有运行配置
DATABASE_URL=postgresql://langfuse:***@postgres:5432/langfuse
# LiteLLM 私有运行配置
DATABASE_URL=postgresql://litellm:***@postgres:5432/litellm
# business 私有运行配置
SUPABASE_URL=http://supabase-gateway:8000
MODEL_BASE_URL=http://litellm:4000/v1
```

切到外部 PG，只修改相应消费者配置并关闭 local-pg。各平台优先保留上游原生变量，不新增全能配置服务或多级 TOML→JSON→env 生成链。

Supabase 部分组件需要 host、port、database、user 等分字段配置；对用户提供 PG URL 输入时可以做一次明确解析，保留 TLS/连接参数，校验 IPv6 与转义，不能无声丢弃 query 参数。无法无损表达的配置必须明确报错或使用上游支持的原生参数。

### 3.3 外部 PG 的能力检查

可达的 PG URL 不等于可运行完整 Supabase。要按启用组件核对：

- PostgreSQL 版本、必要扩展及可用版本。
- 初始化角色、schema、权限及迁移权限。
- 已启用能力需要的服务端设置，例如 Realtime 的逻辑复制能力。
- TLS、直连端点和连接池限制。管理/迁移连接与业务事务池连接分别配置。
- 数据库时区等上游约束，基础存储默认 UTC。

scripts/check.py 默认只读，输出具体缺失能力；不会自动给用户的外部数据库装扩展、改角色或做迁移。新库初始化通过明确的 bootstrap 命令执行，升级迁移使用相应上游入口并单独记录。

## 4. 版本选择：取支持范围交集，再选成熟维护版本

“最大公约数”落实为：固定平台源码版本 → 汇总所有依赖约束与扩展要求 → 计算可用交集 → 选择仍受维护的稳定补丁版本 → 真实集成验证 → 锁定镜像摘要。

不是简单选择最老版本，也不是将每个服务的最新版本拼起来。

截至 2026-10-19 的官方资料核对：

| 项目 | 已核对的依据 | 本项目结论 |
| --- | --- | --- |
| Supabase PG | 官方 Compose 当前采用 supabase/postgres:17.6.1.136，并带角色/JWT等初始化脚本 | PG 17 是优先候选，不能直接换成缺少扩展的普通 postgres 镜像 |
| Langfuse v4 PG | 官方升级指南要求 ≥15，推荐 16；官方 Compose 当前也使用 PG 17 | PG 17 是共同候选，不能只凭主版本声明全平台验证通过 |
| Langfuse v4 Redis | ≥7.0，推荐 7.2 | 以 Redis 7.2 系列为候选，精确补丁及其他消费者兼容性待核验 |
| Langfuse v4 ClickHouse | ≥25.12，推荐 26.4 | 比较 25.12 与 26.4 在锁定组件上的兼容性、维护状态后定版 |
| LiteLLM 与业务 Agent Server | 需要按实际选择的源码/运行版本核对 PG、Redis、迁移与连接池要求 | 当前尚未形成完整版本交集，不宣称 PG 17 已最终定版 |
| RustFS | 不仅检查 S3 接口名称，还要验证调用方所用对象操作 | 上传、读回、预签名 URL、分段上传按启用功能测试后锁定摘要 |

官方依据：

- [Supabase 当前 Compose](https://github.com/supabase/supabase/blob/master/docker/docker-compose.yml)
- [Supabase 扩展与镜像兼容约束](https://supabase.com/docs/guides/self-hosting/custom-postgres-extensions)
- [Langfuse v4 基础设施要求](https://langfuse.com/self-hosting/upgrade/upgrade-guides/upgrade-v3-to-v4)
- [Langfuse 当前 Compose](https://github.com/langfuse/langfuse/blob/main/docker-compose.yml)
- [LiteLLM 生产部署建议](https://docs.litellm.ai/docs/proxy/prod)

主分支资料只是本轮核对依据；实施时保存实际源码 SHA，不能让后续主分支变化隐式更新本项目基线。首轮兼容性检查是明确待办，不编造已验证的具体补丁版本或 digest。

## 5. Compose 组合方式

采用静态 Compose + profiles，不生成不同拓扑文件。根 compose.yaml include 各组件定义；下层也可以通过自身 Compose 独立启动。

- business 默认启用；其余服务通过 profile 选择。
- 四种本地存储分别使用 local-pg、local-redis、local-clickhouse、local-s3。
- 平台按 dbx、langfuse、litellm、supabase 分组。Supabase 内部依赖的必要服务共用 supabase profile。
- 不让平台服务对本地 postgres/redis 等声明硬依赖，否则外部替换会形成悬空 depends_on。
- 同一组件内部可以用健康依赖，例如 Supabase Storage 等待其 REST 服务。
- 跨组件依赖通过连接预检、有限等待以及应用运行期重连处理。观测服务异常不默认阻塞业务。
- Supabase/业务迁移是明确的一次性任务，不在每个 web/worker 容器里并发重复执行。

整体与子 Compose 统一项目名、网络约定及路径解析；禁止通过两套入口同时启动同一服务并共享数据库文件夹。外部服务不存在于本地依赖图，不能通过 Docker 容器状态判断其可用性。

示例为拟定接口，尚未实现：

```dotenv
# .env：全本地组合
COMPOSE_PROFILES=local-pg,local-redis,local-clickhouse,local-s3,dbx,langfuse,litellm,supabase

# 使用外部 PG：只移除 local-pg，并修改各消费者的数据库连接
# 其他本地存储保持原样
```

```powershell
docker compose up -d --wait

# 本机修改 Langfuse 源码后，构建该组件镜像
docker compose build langfuse-web

# web/worker 引用同一新组件镜像时，仅重建这两个容器
docker compose up -d --no-deps langfuse-web langfuse-worker
```

以上单次构建命令以前述 web/worker 共享组件镜像为前提；若采用上游不同产物镜像，则显式构建两个目标。切换服务前按版本要求单独执行迁移、检查兼容性与备份。--no-deps 不代表可以跳过迁移条件。

CI 发布镜像时，在 versions.env 更新对应组件引用，pull 后重建对应服务即可；根 compose.yaml 不变。不可变 digest 或唯一版本标签保证不会把两个不同构建混为同一个版本。

## 6. 源码生产构建与业务开发

保留平台源码构建要求，但以组件为单位：

- 上游支持的 release 配置、适用的 LTO/符号裁剪、前端生产构建、生产 Python wheel。
- 多阶段构建与 BuildKit cache，不把工具链带进运行镜像。
- 组件源码、依赖锁文件、配方和工具链共同决定缓存身份。
- 不默认全量编译，不在普通 up 中更新 submodule。
- 不强求所有平台统一端口/子路径，不写进程监督框架；每个服务直接运行其主进程。
- 同组件的 web/worker、API 与数据库 schema 存在版本耦合，需要成组升级。换镜像不意味着数据能自动回滚。

业务仍由官方 Agent Server 和 http.app 扩展承载工作台、workflow demo 与 deepagent demo。生产镜像装业务 wheel 和前端 dist；开发使用 Dockerfile dev target + compose.dev.yaml，或在宿主机使用 uv 和 Vite。

langgraph dev 的开发状态与正式 PostgreSQL/Redis 持久化分别验收；正式运行入口与授权要求按锁定版本核实，不把关闭热重载当成生产部署。[官方 HTTP 扩展](https://docs.langchain.com/langsmith/custom-routes)、[官方运行方式](https://docs.langchain.com/langsmith/deploy-standalone-server)

## 7. 必须验证的最小集合

1. 全本地组合冷启动、重启后数据读回、绑定文件夹权限正确。
2. 同一平台配置从本地 PG 切换到干净且兼容的外部 PG，确认没有启动本地 postgres。
3. 只配置已有 Supabase API 时不启动本地 Supabase；本地 Auth/REST 配外部 PG 是另一项测试。
4. 各存储可单独外置；S3 内部端点和浏览器公开端点分别验证。
5. 更新 Langfuse 只替换其 web/worker，其他存储和平台容器不重建；迁移流程有明确记录。
6. 外部 PG 缺扩展/权限或 TLS 错误时提供明确诊断，不偷偷启动本地替身。
7. 内置 threads/runs 与业务 HTTP 扩展均验证鉴权；真实模型、Langfuse 追踪、前后端热重载分别验证。
8. 记录兼容性候选与已验证结论，不将旧项目或上游样例的成功算作本项目通过。

实施顺序：锁定平台版本及兼容矩阵 → 独立存储服务 → 连接与 profiles → 各平台源码镜像 → 业务 demo 与开发模式 → 本地/外部替换及独立升级验证。
