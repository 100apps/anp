# 平台性能测量

当前只完成具体链路的测量和调整，不代表全平台或 deep_dub 整片验收已完成。

## 本机连接

同一 Docker 平台、每次新建客户端的健康请求中位耗时：`localhost` 为 2044.856 ms，`127.0.0.1` 为 11.475 ms。规范本机入口已统一为 IPv4；这是连接开销改善，不是业务吞吐或视频 RTF。

## 图执行并发

基准访问平台唯一入口，创建任务、执行 normalize/analyze/save、等待最终状态、查询结果，并下载真实私有对象验证与报告一致。每组 8 个独立任务。

| 客户端并发 | 执行器并发 1：任务/秒 | 执行器并发 4：任务/秒 |
| --- | ---: | ---: |
| 1 | 0.4667 | 0.4940 |
| 2 | 0.9231 | 0.8433 |
| 4 | 1.2960 | 1.1343 |

提高执行器并发没有改善所测 demo 吞吐，因此默认保留为 1。两轮各测一次，同机仍有源码构建与保留的旧平台，不能把差异当作统计显著的因果结论。资源记录是前后快照，不是峰值。需要用实际业务负载再决定参数，尤其不能让图并发替代 CPU/GPU 节点的设备租约与容量限制。

私有部署配置：

```toml
[agent]
max_concurrent_runs = 1
```

支持 1–32，Docker 与原生平台共用配置；变更后重新准备对应运行模式。运行器将其传给官方 `run_server(n_jobs_per_worker=...)`，不增加 Agent 实例。当前使用本地开发版 Agent，不把它描述成生产分布式运行时。

复现命令（先启动平台与本机 API/Worker）：

```powershell
uv run python scripts/benchmark_platform.py --count 8 --concurrency 1 2 4 --output .local/my-platform-benchmark.json
```

脚本使用已配置的管理员登录，创建标题标记为“平台并发基准”的真实测试任务；输出不包含登录令牌。原始测量、资源快照与两条历史线程跨镜像重建的状态校验和见 [测量证据](evidence/v3-platform-concurrency-20261018.json)。执行器并发 4 的试验镜像通过 43 项回归；默认回到 1 后，最终镜像也通过 43 项回归（78.01 秒），官方日志确认启动 1 个后台执行槽位，旧线程仍保留。

## 镜像迭代

组装 Dockerfile 将稳定的第三方根文件系统放在本地 SDK 与运行器源码之前，避免仅修改运行器时使全部大型 COPY 层失效。组件源码 SHA 校验、依赖清单和正式发布门槛保留。

此前同配方的缓存重复组装实测 4.908 秒、24 个步骤命中缓存；该次改变来源提交标签，没有修改运行器源码，因此不能将其描述成冷构建耗时或证明源码改动后的加速幅度。前一版镜像来自干净提交 `2b833f8`，运行器文件哈希一致。详情见 [该版镜像证据](evidence/v3-runtime-final-20261018.json)。

本次实际修改 SDK 和依赖声明后重新组装，十个第三方根文件系统 COPY 步骤全部命中缓存。新镜像来自干净提交 `84922e5`，34 个 SDK Python 文件逐一校验一致；这次验证了源码变化时第三方层的复用，不将其混同于冷构建时间。

## HTTP 证书解析与任务状态查询

客户端创建的独立微基准中，每次使用 HTTPX 默认证书上下文的中位耗时为 7.9562 ms；缓存经校验的 certifi 根证书上下文后为 0.0198 ms（各 50 次，不发网络请求）。SDK 新增统一客户端工厂，保留证书和主机名校验；每次仍新建独立 HTTP 客户端，各自管理请求头、Cookie、连接和关闭生命周期。只缓存证书解析，不缓存登录身份、权限或客户端。

同时测量了任务状态查询并发。提高到 4 未改善吞吐，因此默认保留串行；配置入口为 `settings.local.toml` 的 `[development].coordinator_concurrency`，或 `ANP_DEVELOPMENT_COORDINATOR_CONCURRENCY`，允许 1–16。这与部署配置中的图执行槽位 `[agent].max_concurrent_runs` 分别控制查询和执行，不应混淆。

已修复长任务持续占据首批 50 行造成后续任务无法更新的问题：按稳定顺序分页轮询，并周期回到首批；动态集合缩小时可能暂时跳过部分行，后续扫描会补查。单任务查询失败不终止整批，关闭时取消进行中和等待中的查询。相关契约测试包含超过 50 个长任务、错误隔离、并发上限、取消及客户端身份隔离。

初测与整合镜像复测（各组 12 个真实任务，图执行槽位保持 1）：

| 客户端并发 | 原 SDK：任务/秒 | 查询并发 4：任务/秒 | 宿主证书缓存：任务/秒 | 整合后证书缓存：任务/秒 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 0.5029 | 0.4944 | 0.4872 | 0.6322 |
| 4 | 1.4183 | 1.3579 | 1.7871 | 2.1004 |
| 8 | 1.5720 | 1.4276 | 3.0837 | 3.6441 |

宿主初测时 Agent 仍为旧制品，单任务吞吐未改善；随后把优化整合进 Agent 镜像，再运行得到最后一列。最终镜像通过 48 项回归（62.62 秒），四条历史线程状态保留，且包含真实对象下载一致性、用户权限即时变更、会话与评分检查。

这些结果支持减少客户端初始化的重复开销，不代表所有业务都会得到相同比例的加速。每种配置只有一轮，仍有旧平台后台负载，不作统计显著性或整片配音 RTF 结论。[完整证据](evidence/v3-http-trust-cache-20261018.json)保留全部四轮数据、资源快照、最终镜像来源与源码校验。

## DBX 查询升级基线

当前运行 DBX 源码为 `b3a6159b40e4cc921bff084d57d01e862b6ad614`。新 CI 编译的上游已是另一提交，因此后续对比只能评价整体升级，不能单独把差异归因于关闭 LTO 或增加代码生成单元。

通过平台单端口、DBX 密码鉴权和已有 PostgreSQL 连接，只读执行三个固定查询。每种查询先预热三次，再分别以并发 1 和 4 各发 30 次；延迟包含 HTTP、JSON 解码及结果校验。

| 查询 | 并发 1 中位耗时 | 并发 4 中位耗时 |
| --- | ---: | ---: |
| 常量 SELECT 1 | 1.625 ms | 2.610 ms |
| 10,000 个整数求和 | 2.420 ms | 3.202 ms |
| 返回并校验 1,000 行 | 2.959 ms | 4.261 ms |

重测命令：

```powershell
uv run python scripts/benchmark_dbx.py --count 30 --concurrency 1 4 --output .local/dbx-query-benchmark.json
```

基准不修改业务表或保存连接配置；会建立运行时数据库连接。共享开发机背景负载未隔离，每组样本较少，不能据此宣称统计显著或 deep_dub 实时率达标。新 CI DBX 制品尚未完成构建与同方法复测。[原始样本与版本证据](evidence/v3-dbx-query-baseline-20261018.json)。
