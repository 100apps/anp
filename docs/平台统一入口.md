# 平台统一入口

工作台侧栏提供四个平台的独立入口。沿用 LangGraph Agent Server 的 `http.app` 扩展，Python 后端转发 HTTP、流式响应和 WebSocket。

| 平台 | 统一目录 | 本地独立端口 |
| --- | --- | --- |
| DBX | `/dbx/` | 54224 |
| Langfuse | `/langfuse/` | 53000 |
| LiteLLM | `/litellm/`（进入 UI） | 54000 |
| Supabase Studio | `/supabase/` | 53001 |
| Supabase API | `/supabase/auth/v1/`、`/supabase/rest/v1/`、`/supabase/storage/v1/` | 58000 |

开发入口为 `http://127.0.0.1:51730/workbench/`，业务容器入口为 `http://127.0.0.1:52024/workbench/`。Vite 将同一组目录转发到本机后端 20240，保留请求来源。平台没有启动时显示明确的 503 页面；工作台不依赖平台全部启动。

## 启动与更新

```powershell
make bootstrap
make build-platform
make platform
make dev
make platform-check
# 容器入口验收
make platform-check PLATFORM_URL=http://127.0.0.1:52024
```

首次构建需访问各官方包仓库，耗时和内存显著高于日常启动。构建与启动分开；普通 `make dev` 仍只启动四存储及业务开发环境。单组件更新使用 `make build-platform COMPONENT=组件服务名`，然后用固定项目 `anp2-next` 的 Compose 仅重建该服务。Langfuse web/worker 应使用同一源码版本。

## 外部平台与路径配置

`config/services/platform-proxy.env.example` 提供宿主开发配置，按需写入 `business/.env`。业务容器默认使用 Docker 网络服务名，也可在根 `.env` 覆盖 `ANP_PLATFORM_*_URL`。这些地址只由后台配置决定，浏览器不能指定目标服务器。

地址必须包含上游实际部署的目录：本项目四个平台分别带 `/dbx`、`/langfuse`、`/litellm`、`/supabase`。LiteLLM 的 UI 在启用 `SERVER_ROOT_PATH` 后也要求保留此前缀。对方若部署在根目录，应相应调整目标地址及对方公开地址配置。代理不注入管理员凭据，平台维持自己的登录机制。

对外规范地址由根 `.env` 的 `ANP_PUBLIC_URL` 控制，默认 `http://127.0.0.1:52024`。需要将开发端口作为 OAuth 等回调入口时，显式改成 `http://127.0.0.1:51730` 并重建对应服务容器；同一时刻只有一个规范回调地址。

DBX、Langfuse 和 Studio 的目录属于构建配置，修改后要重新编译镜像。Langfuse 的 `NEXTAUTH_URL` 包含 `/langfuse/api/auth`。LiteLLM 使用运行配置 `SERVER_ROOT_PATH=/litellm`。Studio 锁定源码的浏览器 API 地址仍硬编码 `/api`，构建配方在镜像内增加目录前缀；不修改 submodule 工作树。

生产配方来自锁定的真实 submodule，由 `scripts/source_recipes.py` 同步，并在 `docker/source-recipes.json` 记录上游 SHA、配方 SHA256 及适配原因。LiteLLM 使用官方公开 Wolfi 软件仓库和已有签名密钥，源码归档保留上游 SHA256 校验；Dashboard 使用 Next.js 的生产 Webpack 构建以避开当前 Turbopack 内部错误。PostgREST 用 `path:/src#static` 构建，避免容器内解析宿主 submodule 的 `.git` 相对路径。

## 验收边界

`make platform-check` 检查四个真实平台页面、同目录 JS/CSS 资源，以及 Langfuse/LiteLLM 健康接口、Studio 项目接口和 Supabase Auth/REST/Storage 接口。有任一平台未启动就失败。代理契约测试另外覆盖请求体、Cookie、重定向、压缩、SSE、Range、WebSocket 和路径约束，契约测试不能代替真实平台验收。

管理台仅供回环地址本地使用。未在本轮验收的平台注册、供应商模型调用和平台内写入业务操作，不列为已通过；译配真实模型链路的验收记录独立保存在视频译配文档中。

2026-10-20 本地验收：四个平台源码镜像均已构建并运行；20240 后端、51730 开发前端、52024 业务容器入口均通过。每个入口分别验证 DBX 3 个、Langfuse 67 个、LiteLLM 43 个、Studio 98 个首屏静态资源。浏览器实际打开三个登录页，并在 Studio 表编辑器读取了 `dubbing.runs` 记录和外键关联入口。

业务与 Compose 测试共 34 项通过，前端生产构建、演示及生产业务镜像构建通过；四存储读写、两类 demo 的宿主与容器 HTTP 流式调用通过；已有真实译配运行的重放及媒体 Range 206 通过。译配数据库测试使用临时空间并清理本次夹具数据。开发日志管道修复后，实际检测到 `platforms.py` 变化并完成热重载。旧环境 49 个容器的 ID/启动时间基线保持不变。

LiteLLM 默认使用镜像内锁定版本的模型价格表，避免启动时依赖 GitHub 联网；更新价格表随组件镜像显式升级。`make platform` 通过 readiness 等待 LiteLLM 完成启动，平台源码构建仍不会被启动命令隐式触发。
