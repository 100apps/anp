# 镜像体积优化

2026-10-20 本机实测。保持全部14个服务和现有功能，不设置1GB硬上限。默认 `anp3/toolbox:local` 已切到优化后的 Zstd 版本。

## 实际体积

| 版本 | Docker 本地磁盘占用 | 分发内容大小 |
| --- | ---: | ---: |
| 原始完整镜像 | 约10.97GB | 约2.28GB |
| 精简文件、gzip压缩 | 约9.25GB | 约1.94GB |
| 精简文件、Zstd压缩（当前） | 约8.72GB | 约1.42GB |

本地占用减少约21%，分发内容减少约38%。Docker Desktop 当前使用 containerd 镜像存储，`docker image ls` 同时列出 DISK USAGE 和 CONTENT SIZE；本地占用包含展开层和压缩内容，不能把1.42GB下载量说成本地只占1.42GB。截图中的10.97GB属于前一口径。压缩无法让运行时展开文件同比缩小。

当前镜像身份：`sha256:20608ea3ae59cb517cbacf2da0fc611c1335465c8ababbae94ff6969ee9675e9`。

## 已做的优化

- 多阶段构建只组装生产运行产物，清理源码映射、安装缓存字节码、Storage附带的Python/GCC/npm构建工具和静态库。
- 完全相同的 Redis 辅助程序改为符号链接，保留命令。移除未使用的 Node 26，保留实际使用的 Node 24、Meta所需Node 22以及Storage独立musl运行库。
- 对 Node 依赖中的相同内容做硬链接去重，保留所有包路径；没有盲目删除动态加载的供应商SDK。
- 清理后用 scratch 阶段重新复制运行文件系统，避免删除文件仍占据旧镜像层；导出使用 Zstd 压缩。

构建内置清理报告记录删除约923MB逻辑文件、去重约323MB逻辑文件；它们不是可直接相加的Docker磁盘回收量。最终结果以上表实际测量为准。完整 PostgreSQL 扩展、Java、官方二进制和服务所需的不同ABI仍保留。ClickHouse和RustFS二进制本身合计已超过1GB，全功能镜像的本地占用压到1GB并不现实。

扁平化单层的代价是更新组件时可能重新分发大部分内容。当前优先降低完整交付包体积；未来若更关注频繁更新，可以重新评估分层缓存与传输量的取舍。

## 使用

```sh
make image-size
make image-export
# 目标机器已安装支持Zstd的Docker：
docker load -i var/images/anp3-toolbox-20608ea3ae59.tar.zst
make up
```

本次导出包 `var/images/anp3-toolbox-20608ea3ae59.tar.zst` 为 **1,419,252,783字节**，SHA256：

```text
bbea576499b0d85ec67bd41f12b68e074de154000b9603dfe0699ac5dd1d5f66
```

包内只有镜像，不含 `/data` 持久化数据，换机器仍需单独备份和迁移数据根。导出为流式处理，不生成十几GB的未压缩中间包。旁边的JSON保存大小与校验值。该包已通过 `docker load` 实际导入，导入后运行配置与文件系统层完全一致。仅导出linux/amd64会移除外层索引和构建证明，因此导入后的平台镜像ID与原索引ID不同，不能仅比较这两个ID判断内容变化，见[导入证据](evidence/image-import.json)。

`make build` 默认使用 buildx 的 Zstd 输出；源码组件生产构建仍由 `make build-components` 单独执行。现存原始镜像标签、组件构建镜像和构建缓存继续保留用于回滚，不执行全局Docker清理，因此宿主Docker总磁盘不会自动减少到8.72GB。
